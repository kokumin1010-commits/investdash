## 代码根因

`buildAssetTrend` 按日/月 bucket，并用同 bucket 最后一条覆盖前面记录；这是合理的日次聚合，但数据只有一天时无法显示“推移”。`syncPrices` 每次都会插入新 snapshot，没有日级 upsert；因此同日手动更新会增加原始记录，却不会增加图表点。

`enrichProfiles` 只处理前 20 条缺失 holding 和前 20 条 watch item，返回的只是本次成功数，没有 offset/nextOffset。Settings 手动执行一次并不能覆盖 156 条账户记录。

`regenerateAllSignals` 已经按 symbol 去重并支持 offset/batchSize，但重建后只对 Toyota 做过单标的生成。`listPlanOverview` 只遍历现有 price-band plan，因此计划页要增加真实行，必须先批量建立计划。

## 修复原则

资产快照保持“每日一个图表点”，但在价格同步时对当日记录做 upsert，并由 Railway 每日行情任务持续产生新日期。行业、信号和计划都按去重 symbol 批处理，记录 processed/failed/nextOffset；不能用模拟分类、默认信号或伪造价格带填满页面。

## 批量补全设计

所有目标集合都以去重后的 `symbol` 为单位，而不是 156 条券商账户行。企业资料每批最多 20 个 symbol；信号每批最多 4 个；价格带每批最多 2 个。AI 类任务串行执行并设置进程级互斥，避免 Railway 上一次任务尚未结束时重复进入。

企业资料补全按稳定排序的目标列表接收 `offset` 和 `batchSize`，一次 Yahoo 请求后使用 `updateHoldingBySymbol` 写入该 symbol 的全部账户行，并同步更新相同 watchlist symbol。返回 `total / processed / updated / failed / skipped / nextOffset`，无资料的标的保留为明确的“未取得”，不写入虚构行业。

信号批量只选择当前没有 signal 的持仓，不覆盖 Toyota 等已有判断。价格带批量只选择没有 plan 的持仓，不覆盖人工编辑或已经生成的计划。两者都通过现有 `aiRunLogs` 留下成功和失败记录；失败 symbol 在自动任务中进入冷却期，手动批次仍可显式重试。

Railway 常驻调度器增加低频维护窗口。每次只运行一个小批次，依次推进资料、缺失信号和缺失价格带；与行情、新闻任务分别设置互斥锁。任务每次重新从数据库计算仍缺失的目标，因此部署重启后可续跑，不依赖内存 cursor。永久失败不会阻塞其他 symbol：自动批次会参考最近失败日志进行冷却，返回剩余数并在界面显示。

买增总览继续只把已有真实 plan 当作可执行计划，但新增覆盖状态数据，页面会同时列出“未作成”的持仓并显示生成进度。这样不会把占位价格误当成建议，也不会再只显示 Toyota 而掩盖其余 111 个待生成标的。
