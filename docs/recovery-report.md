## 恢复结论

InvestDash 已从 GitHub 仓库重建并部署到 Railway，公开入口为 [https://salesdash.buzzdrop.co.jp/investdash/](https://salesdash.buzzdrop.co.jp/investdash/)。新服务沿用原有业务模型和 25 个 Drizzle 迁移，恢复了个人パスコード访问、投资组合仪表盘、持仓、资产内訳、ウォッチリスト、卖买/月次记录、行情更新、企业基础资料、新闻抓取以及分析服务。界面品牌统一为 **InvestDash / PRIVATE PORTFOLIO OS**，并针对 390 px 手机视口重新完成卡片、筛选和导航验收。

旧网址仍属于平台数据迁移后的待恢复项目；在没有 `.manustask` 备份的情况下，旧数据库和运行历史不能由源码直接取回。官方恢复说明同样要求使用原始备份包执行恢复，因此本次采用“新项目 + GitHub 可重建数据”的方式，而不是继续修改旧网址。[1]

## 无法从仓库恢复的数据

| 数据缺口 | 原因与处理 |
|---|---|
| 2026-07 及更早月次明细 | 仓库没有逐标的数量、成本和价格；未创建估算数据 |
| 旧新闻与 AI 分析历史 | 仅存在于旧数据库运行记录；新环境从真实来源重新积累 |
| 投资咨询对话与信号历史 | 未写入 GitHub；保留空状态，不制造历史 |
| 导入图片与旧上传文件 | 旧对象存储内容不在源码仓库 |
| 部分价格带与运行配置 | 只恢复仓库中有明确数据来源的内容 |

> 本次恢复遵循“可验证才恢复”的原则。对没有原始明细的数据，不使用估算值填充，以避免将推测误认为真实投资记录。

## Railway 数据架构

SalesDash 与 InvestDash 共用一个 Railway MySQL 实例，但使用两个逻辑数据库。InvestDash 使用 `railway` database，SalesDash 使用 `salesdash` database；SalesDash 已切换到 `salesdash_app` 最小权限账号，该账号对 InvestDash database 没有表访问权限。SalesDash database 已应用现有 schema（326 张表）和两条 Drizzle 迁移基线，未导入或编造业务数据。

InvestDash 的截图历史使用挂载在 `/data` 的独立 Railway volume。SalesDash 主站通过同项目私网地址 `investdash.railway.internal:8080` 代理 `/investdash`，公开域名只暴露统一 HTTPS 路径。

共享 MySQL volume 已启用 Railway 原生日、周、月自动备份。日备份保留 6 天、周备份保留 1 个月、月备份保留 3 个月；核验时已有 `2026-08-25 19:45`、大小 `1.62 GB` 的可恢复快照。完整恢复步骤与限制见 `docs/railway-backup-runbook.md`。

## 定时任务方案

Railway 服务内置调度器已经自动启用。日本市场收盘后行情更新安排在平日 JST 15:30，美国市场收盘后更新安排在平日 JST 06:30。每日新闻从 JST 07:00 开始，123 个去重标的按每批四个、每五分钟一批拆分为 31 个任务，最后一批在 JST 09:30 执行。

| 工作内容 | 日本时间 | UTC cron | 数量 |
|---|---:|---|---:|
| 日本收盘后行情 | 平日 15:30 | `0 30 6 * * 1-5` | 1 |
| 美国收盘后行情 | 平日 06:30 | `0 30 21 * * 1-5` | 1 |
| 每日新闻抓取与分析 | 每日 07:00–09:30 | 从 UTC 22:00 起每五分钟一批 | 31 |

调度器根据 Railway 环境自动启动，不依赖浏览器、Manus cron 身份或额外的 33 个外部回调。生产手动实测已更新 167 条行情、失败 0；新闻实测新抓取 2 条并成功分析 14 条。

## 2026-08-26 数据完整性升级

本轮在 Railway 生产环境完成了投资卡、价格带确认和后台运行记录升级。112 个去重持仓均已有投资卡，112 次 `card_draft` 运行全部成功、失败 0；每次只补空卡，不覆盖已有人工内容，并对失败设置冷却和手动重试。卡片允许个别无法从真实资料验证的字段保持空白，例如 NVDA 为 5/6 项，不用默认目标价填满。
