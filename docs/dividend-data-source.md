# 配当データの取得元の調査

## 使える API（Manus Data API 経由の Yahoo Finance）

プロジェクト内では `callDataApi` 経由で呼ぶ（`server/_core/dataApi.ts`）。
Python の `data_api.ApiClient` は使わない。

| API | 配当関連で得られるもの |
|---|---|
| `YahooFinance/get_stock_chart` | `events: "div,split"` を指定すると配当の支払履歴（日付と 1 株あたり金額）が取れる |
| `YahooFinance/get_stock_profile` | `summaryDetail.dividendYield`（利回り）、`dividendRate` など |
| `YahooFinance/get_stock_insights` | 配当そのものではなく分析指標 |

既に `get_stock_chart` は株価取得で、`get_stock_profile` は業種取得で使っている。

## 方針

`get_stock_chart` に `events: "div,split"` と `range: "1y"`（または 2y）を付けて
**実際の支払履歴**を取得し、直近 12 か月の合計を「年間配当（実績）」とする。
理由は次の通り。

1. 予想値（`dividendRate`）は日本株・SGX 銘柄で欠損が多い
2. 実績なら「いくら受け取ったか」が明確で、REIT の変動配当にも対応できる
3. すでに使っている API なので新しい依存を増やさない

利回りは `年間配当 ÷ 現在値` で自分で計算する（Yahoo の利回りは基準日がずれる）。

## 株式分割: Yahoo の配当額は**すでに分割調整済み**

最初は「Yahoo の配当額は分割調整されていない」と判断して補正を入れたが、
**これは誤りだった。** 検証の経緯と結論を残す。

### 誤解のきっかけ

日本製鉄（5401.T）の配当履歴が次のようになっていた。

| 日付 | 配当額 |
|---|---|
| 2024-09-27 | 16 円 |
| 2025-03-28 | 16 円 |
| 2025-09-29 | **60 円** ← この日に 5:1 の分割 |
| 2026-03-30 | 12 円 |

16 → 60 → 12 という並びを見て「60 円は分割前基準の額（12 × 5）」と考え、
分割日以降の比率で割る補正を入れた。

### 検証で分かったこと

住友商事（8053.T、2026-06-29 に 4:1 分割）で株価と配当の関係を確認した。

まず**株価は分割調整済み**だった。分割日前後の終値は
1,550.25 → 1,532.5 と連続しており、1/4 に飛んでいない。

次に各配当日の「配当額 ÷ その日の株価」を計算した。

| 日付 | 配当 | 株価 | 比率 |
|---|---|---|---|
| 2024-09-27 | 16.25 | 832.25 | 1.95% |
| 2025-03-28 | 16.25 | 884 | 1.84% |
| 2025-09-29 | 17.5 | 1,070.5 | 1.63% |
| 2026-03-30 | 20 | 1,463 | 1.37% |

分割前の配当（2024-09-27 など）も、調整済み株価に対して
半期利回り 1.3〜2.0% という妥当な水準に収まっている。
もし配当額が未調整なら 4 倍の 5〜8% になるはずで、そうなっていない。

**つまり Yahoo は配当額も株価と同じ基準（分割調整済み）で返している。**
補正を入れると二重に割ることになり、利回りが 1/N に過小評価される。

実際、補正を入れた状態では次のように不自然な値になっていた。

| 銘柄 | 補正後（誤り） | 補正なし（正しい） |
|---|---|---|
| 8053.T 住友商事 | 0.52% | 2.09% |
| 5801.T 古河電気工業 | 0.05% | 0.52% |
| 8309.T 三井住友トラスト | 0.67% | 2.66% |
| 7735.T SCREEN | 0.51% | 1.03% |

### では日本製鉄の 60 円は何だったのか

**特別配当（記念配当）である。** 配当日の株価と比べると明確になる。

| 日付 | 配当 | 株価 | 比率 |
|---|---|---|---|
| 2024-09-27 | 16 | 649.2 | 2.46% |
| 2025-03-28 | 16 | 657.8 | 2.43% |
| 2025-09-29 | **60** | 620 | **9.68%** ← 突出 |
| 2026-03-30 | 12 | 574.7 | 2.09% |

他の期は 2.1〜2.5% で揃っているのに、2025-09-29 だけ 9.68% と突出している。
分割の影響ではなく、その期だけ特別に多く払ったということ。

### 結論と実装

**分割補正は行わない。** `splitFactorAfter` などの関数は残してあるが
（将来 Yahoo の仕様が変わった場合の備えとして）、既定では適用しない。

代わりに**特別配当の検出**を行う。1 回の配当がその銘柄の
平均的な 1 回あたりの配当額を大きく超える場合、
「一時的な配当が含まれている」ことを画面で示す。
こうすれば「来年も同じだけもらえる」という誤解を避けられる。

## 特別配当の検出が効かないケース

日本製鉄（5401.T）の実データは直近 1 年で 2 回しか支払がない。

| 日付 | 配当 |
|---|---|
| 2025-09-29 | 60 円（特別配当を含む） |
| 2026-03-30 | 12 円 |

検出ロジックは「支払 3 回以上」を条件にしている。2 回では
「期末配当が中間配当より多い」という通常のパターンと区別できないため。
その結果、日本製鉄は特別配当として検出されず、
年間 72 円・利回り 10.65% と表示される。

この数字は**直近 1 年の実績としては正しい**が、
来期の見込みとしては過大（平常時は年 24〜32 円程度）。

### 対応

利回りが異常に高い銘柄には画面で注意を促す。
具体的には**利回り 8% 超**を「要確認」として表示する。
8% という基準は、実在する高配当銘柄（REIT や資源株で 6% 台）を
誤って警告しない水準として選んだ。

2 回だけの支払で誤検出のリスクを取るより、
「実績をそのまま出して、異常値には注意を促す」方が誤解が少ないと判断した。

### range パラメータの注意

`range: "3y"` を指定すると配当イベントが空で返ることがあった（5401.T で確認）。
`1y` / `2y` / `5y` では正常に返る。**`2y` を使う。**
2 年分あれば直近 1 年の集計に加えて分割の検出もできる。

## 税金の扱い

配当には source によって異なる税がかかる。

| 市場 | 現地源泉税 | 備考 |
|---|---|---|
| 日本株 | 20.315% | 特定口座なら源泉徴収済み |
| 米国株 | 10%（日米租税条約） | さらに日本で 20.315%（外国税額控除の対象） |
| シンガポール株 | 0% | SGX は配当課税なし（REIT の一部を除く） |

**方針: まず税引前（gross）で表示する。** 口座の所在国や個人の状況で
実際の手取りは変わるため、税引後の額を一律で出すと誤解を生む。
将来的に必要になれば設定で切り替えられるようにする。

## 実装した画面（2026-08-16）

### ダッシュボード
- サマリーに「年間配当（税引前）」カードを追加。年間額・月あたり平均・
  現在値利回り・取得原価利回り・配当あり/無配の銘柄数を表示
- 特別配当を含む銘柄がある場合は、それを除いた年間額も併記
- 「国・市場別の資産」「証券口座別の資産」の各カードに年間配当と利回りを追加
- ヘッダに「配当更新」ボタンを追加（20 銘柄ずつ分割実行）

### 保有一覧
- スマホ: カードに「年間配当」「買った値段に対する利回り」を追加
- PC: 表に「年間配当」列を追加。利回りが 8% 超または特別配当を含む場合は
  警告アイコンとツールチップで理由を説明
- 複数口座で持つ銘柄は内訳行にも口座ごとの配当額を表示
